# B-04 — قبول Android المتبقي

الحالة عند إعداد الوثيقة، 23 أكتوبر 2026 بتوقيت عدن: **PENDING_DEVICE_TEST**.
لم يُبنَ APK في البيئة السحابية: Android SDK غير موجود، ومستودعه محجوب من
الـproxy. هذه خطوات قبول لاحقة، وليست سجل نجاح على هاتف.

## شروط البدء

1. بيئة Android SDK/JDK متوافقة، وجهاز Android فعلي 6GB موثق الطراز/OS/ABI.
   يسجل Emulator دليلًا إضافيًا؛ لا يغني وحده عن قياسات الجهاز المستهدف.
2. تثبيت اختبار منفصل بمعرّف تطبيق مختلف عن أي تثبيت مستخدم؛ لا تُستبدل نسخة
   عليها حساب أو بيانات حقيقية. إعداد معرّف الحزمة المنفصل والتحقق منه شرط قبل
   تثبيت الاختبار على جهاز يستعمله الطالب.
3. التنفيذ من فرع B-04 في **siraj-codex** فقط. لا نسخ من المشروع الأصلي ولا
   حاجة للوصول إليه. تستعمل الاختبارات `b04_test` وSQLite مؤقتة؛ نطاق الاختبار
   غير مسموح به في build غير debuggable.
4. بوابة Auth الإنتاجية تبقى مغلقة. لا تُعدلها لإنجاح اختبارات القبول.
   الاختبار المعزول يستخدم AuthService وKeystore الفعليين وإعداد KDF المرشح.

## أوامر الفحص

```bash
flutter --version
dart --version
flutter doctor -v
flutter devices
flutter pub get --enforce-lockfile
flutter analyze
flutter test
flutter build apk --debug --no-pub
# بعد التحقق من عزل التثبيت ومعرّف الحزمة:
flutter test integration_test/b04_android_secure_session_test.dart -d <ANDROID_DEVICE_ID> --reporter expanded
```

اختبار Android الموجود حُدّث ليستخدم **600000** تكرار بدل **1000** التجريبية،
ويشمل كلمة مرور خاطئة، SQLite reopen، واستعادة الجلسة وLogout/Login/Delete
وبقاء المورد المشترك. زمنه المحدود ليس اعتمادًا تلقائيًا للأداء. إعادة فتح
SQLite في الاختبار **ليست** Force-stop أو إعادة تشغيل فعلية للتطبيق.

لإعادة قياس Linux فقط يمكن تشغيل:

```bash
dart run tool/b04_kdf_benchmark.dart
```

هذا الأمر يقيس جهاز تشغيل Dart، ولا يقيس الهاتف المتصل.

## مصفوفة القبول الفعلي

| الحالة | الإجراء والدليل المطلوب | شرط القبول |
|---|---|---|
| KDF security candidate | ثلاث عمليات cold/warm على الأقل عند 600000؛ توثيق نسخة الكود والجهاز ووقت البدء/الانتهاء | مراجعة أمنية وأداء الجهاز قبل تثبيت Config الإنتاجي؛ لا خفض تلقائي للتكرارات |
| استقلال UI عن KDF | عرض Loading والتفاعل/رسم الإطارات أثناء الاشتقاق؛ CPU/RAM وframe timings | لا ANR/تجمد؛ عمل CPU في Isolate؛ لا اعتبار heartbeat السحابة دليلًا للهاتف |
| Cancel | إلغاء قبل حفظ الحساب وأثناء KDF، ثم إعادة المحاولة | العامل يتوقف، لا حساب قبل COMMIT؛ إذا حُفظ الحساب بالفعل ينتقل التدفق إلى Login |
| إنشاء الحساب | Signup بمدخلات اختبار صالحة؛ فحص طول salt/hash واسم الخوارزمية دون طباعتها | حساب واحد؛ لا plaintext password في SQLite/Prefs/Logs |
| Login | كلمة صحيحة وأخرى خاطئة؛ محاولتان متزامنتان | الصحيحة فقط تنشئ جلسة؛ الثانية المتداخلة تفشل typed busy؛ لا Marker/DB mismatch |
| Secure Session | حفظ Marker واستعادته عبر القناة الحقيقية | AES-256-GCM وAndroidKeyStore؛ لا plaintext fallback |
| Restart حقيقي | Force-stop ثم فتح التطبيق، ثم إعادة تشغيل الهاتف | الحساب والجلسة الصحيحة يستعادان دون كلمة مرور؛ سجل العملية الفعلية منفصل عن SQLite reopen |
| Logout | خروج ثم Force-stop وفتح؛ إعادة Login صحيحة | nonce ملغاة في DB قبل نجاح Logout؛ Marker قديم لا يدخل |
| فشل Logout | تعطيل كتابة DB في build اختبار معزول ثم Retry | لا إعلان نجاح؛ الجلسة محجوبة للعمليات الحساسة، ويمكن إعادة المحاولة |
| Delete | تأكيد النص المعتمد، ثم إعادة تشغيل وإنشاء حساب جديد | حذف User/Conversation/Message/Settings؛ الموارد باقية؛ epoch جديد؛ القديم لا يكتب |
| خطأ Keystore / مفتاح مفقود | حقن عطل في بيئة اختبار معزولة فقط؛ لا حذف مفاتيح إنتاجية | لا دخول تلقائي أو حذف للحساب؛ خطأ آمن؛ إعادة المصادقة الصحيحة تعالج الحالة القابلة للاستعادة |
| تلف Ciphertext | تعديل مادة اختبار معزولة واختبار tag/UTF-8/الحجم | فشل مغلق؛ لا بيانات غير موثقة أو استبدال تلقائي بالواضح |
| Lifecycle | إعادة إنشاء Activity/Engine أثناء عملية؛ قراءة/كتابة/مسح متتابعة | لا callback قديم يكتب فوق جلسة أحدث؛ لا thread جديد متسرب لكل Engine |
| Backup / transfer | فحص merged manifest وAndroid backup/restore وdevice transfer على الجهاز | لا استعادة DB/Marker بمفتاح غير متاح؛ سياسات XML لا تكفي لإعلان نجاح OEM |
| التكرار والذاكرة | تكرار التسجيل/الدخول/الخروج والإلغاء مع رصد الذاكرة | لا تراكم workers/طلبات؛ تقرير RSS/heap/native منفصل؛ لا استنتاج leak-free من ثلاث عينات |

## بوابة التفعيل

بعد نتائج الجهاز ومراجعتها: تثبيت إعداد KDF المبرر، ثم ربط production AuthService
في AppBootstrap مع Signup/Login ومسارات Logout/Delete ضمن تغيير مستقل قابل
للمراجعة. لا تُستخدم ثوابت 10/1000 من Unit Tests، ولا حسابات اختبار أو
`dart-define` لتجاوز البوابة.

يُسجل لكل صف PASS/FAIL/PENDING_DEVICE_TEST مع SHA والجهاز وOS/ABI والتوقيت
والقياس الفعلي. تُحذف كلمات المرور والـnonce والمفاتيح والـhashes الخاصة
والمعرّفات الشخصية من الأدلة؛ لا يُرفع Logcat كامل أو قاعدة بيانات أو مفاتيح.
